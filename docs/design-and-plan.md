# ZOTA Net 0.1.0-rc1: первая интеграция

Основание: реальные ответы zota-diagnostic.json от 2026-10-06. Вход и все три метода чтения успешны. SOLID_X, текущие данные: Power=1.5 кВт, Water=26°C, Air=217°C, DHW=Ошибка датчика. История: TempRoom=215/217, Pressure=1101–1105; невалидные температуры 16385. Stages в REST уже содержит начальный ноль; историческая ступень 1 соответствует Stages[1]=1.5, в отличие от массива графика сайта.

## Границы

Только чтение Solid X. Одна запись HA на аккаунт, выбор нескольких котлов. UI-вход, восстановление после истечения токена, облачный опрос каждые 60 секунд; история раз в 300 секунд за последний час с offset=1. HTTP требует явного согласия в форме; TLS-проверка никогда не отключается; редиректы отклоняются.

Текущие сенсоры: мощность, ступень, температура теплоносителя, температура помещения, ГВС, статус, количество ошибок/предупреждений. Air для Solid X с типичным целочисленным масштабированным значением /10; уже дробное или правдоподобное градусное значение не делится повторно. Это совместимость с наблюдаемым серверным форматированием, а не универсальное правило для остальных котлов. Unknown и коды ≥16384 не заменяются нулём.

Исторические сенсоры: давление /1000, температура радиатора, температура улицы, дата последней точки. Числовые исторические сенсоры недоступны после 15 минут без новой точки (настраивается). Отдельный binary_sensor показывает свежесть истории. Актуальный ответ облака не объявляется подтверждением online котла: у current нет timestamp. Ошибки истории не уничтожают успешно полученные current; ошибка авторизации запускает reauth.

Управление котлом, импорт прежней истории в recorder, energy-счётчик, точные коды аварий и другие модели не входят в эту версию. Числовые сенсоры с measurement автоматически дают собственную статистику HA после подключения.

## Файлы и выполнение

1. api.py: aiohttp-клиент, URL/HTTP checks, вход/обновление токена, Result/HTTP checks, чтение current/history, парсинг чисел и точек. Тесты через реальный локальный aiohttp server: контракт входа, повтор после 401, ошибки при HTTP200, редиректы; реальный diagnostic для масштабов и sentinel.
2. coordinator.py: общий токен на аккаунт, выбранные устройства, кеш истории и интервалы, APIError/AuthError → UpdateFailed/ConfigEntryAuthFailed. __init__.py: setup/unload платформ. Проверка через установленный Home Assistant 2024.12.5 (Python3.12); свежие версии требуют отдельной runtime-проверки у пользователя.
3. config_flow.py: вход, согласие HTTP, выбор SOLID_X, reauth, options для интервалов. sensor.py / binary_sensor.py: stable unique_id и DeviceInfo. translations ru/en, manifest, hacs.json, README и license.
4. Проверить полный suite, компиляцию, сохранение без паролей/токенов в fixtures. Упаковать исходники и custom_components в один архив. Без внешнего репозитория возможна ручная установка; HACS требует GitHub custom repository.

## Критические случаи

Пустая/неотсортированная/будущая история; реальная неизвестная температура; Air уже 21.7°C; токен истёк; HTTP200/Result!=0; API возвращает HTML; история недоступна при успешном current; перенаправление на другой адрес; выгрузка entry во время запросов. Все сообщения логов локально сформированы, не содержат JSON ответа, URL query или credentials.

## Наблюдения

API history за сутки с offset=15 вернул только семь точек 09:50–10:25 UTC; полнота суточной истории не доказана. GetBoilerHistoryDate возвращает первую точку 2026-07-29T11:25:00Z. expires_in=2592000 соответствует 30 суткам при стандартном значении в секундах; клиент всё равно восстанавливает вход после 401.
